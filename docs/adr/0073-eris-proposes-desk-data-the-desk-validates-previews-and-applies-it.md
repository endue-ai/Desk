# Eris proposes desk data; the desk validates, previews and applies it

## Context and Problem Statement

Views are data (ADR 0032), and Desk is meant to be shaped by talking: "show my events this week as a
board" should become a view the person sees over their own items before keeping it. A brain writes
text. It can answer in prose, invent a component or a field, or name a source the desk does not have.
Who decides the shape of the answer, who checks it, where is it shown before it is kept, how is it
written, and how is it taken back? Profiles and key bindings (#340) and themes (#312) ask the same
questions, so the answer should not be one for views only. `brain.ask` (ADR 0059) asks the brain one
question in a session of its own and answers with the arguments of a tool call the caller offers;
the theme studio's Describe (#312) asks through it.

## Decision Drivers

* Nothing a brain says lands or runs unchecked: the desk checks it with the schema the core checks a
  file with, and the core checks it again when it writes
* The person sees it over live data before it is kept, and can say what to change or drop it
* What was applied can be taken back in one step, the inverse `cmd.undo` (#276) will call
* The answer comes back as values, never read out of prose and never in the person's conversation
* The app's CSP stays `script-src 'self'`, and no heavy dependency joins the runtime
* One pipeline for every kind of desk data, views first

## Considered Options

* The brain answers a value of the kind's spec schema; the desk fills in its own part, checks it,
  previews it, applies it through the core's own method and keeps the inverse
* The brain writes the file itself, through a tool the core runs for it (`fs.write`, `view.save`)
* Eris's plugin (`endue.eris`) owns the flow
* For asking: `brain.ask` with the kind's tool; `brain.say` with the schema in the prompt and the JSON
  read out of the answer
* For the check: Ajv in the webview; Ajv's standalone code generated by `just codegen`; a small
  interpreter of the keywords the specs use; only the core's check at `view.save`

## Decision Outcome

Chosen option: "the brain answers a value; the desk checks, previews, applies and keeps the inverse",
asked through `brain.ask`, with "a small interpreter" for the check, because the person and the desk
stay between the brain and the disk, and every kind reuses the same steps.

* **Kinds.** `packages/runtime/src/propose`: `createProposals` runs a kind, which gives its tool (a
  name, a description and a self-contained schema bundled from `specs/`), the same schema without
  annotations for a retry to repeat, its context, check, preview, apply and undo. `view` is the first
  (`view.ts`).
* **Asking.** `brain.ask { prompt, tool, scope: brain:ask }` (ADR 0059), under the runtime's grant.
  The prompt holds the sentence, the corrections, the kind's guide, the context and the last proposal
  within brain.ask's 32000 characters (the last proposal, then the context, go first when it would
  not fit). The answer is `structured` on the completed `brain.turn`, which the core sends only when
  the arguments match the tool's schema; a brain that answers in words or with arguments the schema
  refuses gives no value, and the desk never reads JSON out of words. Offline, Eris says the core's
  sentence and the ask waits. There is no `brain.say` fallback: the core serves `brain.ask` wherever
  it serves `brain.say`.
* **The desk's part.** The brain does not write a view's `id`, `version` or `provenance`: the desk
  names it `eris.<slug of its title>` (`-2`, `-3` when taken), gives it 0.1.0 and records author
  `eris`, the time, the person's words and the brain.
* **Checking.** `Schemas` checks a value against the spec files themselves, by their `$id`, with the
  keywords they use; a unit test holds it to Ajv's verdict on every view, item, plugin and connector
  vector. `viewProblems` adds the names a schema cannot check. An answer that fails is asked for once
  more with its problems, each a pointer and what is wrong; an answer with no value (the core says no
  more than that) is asked for again with the compact schema in the prompt. A second failure stops
  with a notice naming the problems and one line from Eris.
* **Preview.** `desk.views.preview { view, note }` draws the view over live data in a floating card
  with Apply, Try again (with a correction) and Discard, and answers with the person's choice as
  `desk.palette.pick` does. Try again asks the brain again with the correction and the last proposal.
* **Apply.** `view.save`, not a raw `fs.write`: the core checks the view again and writes
  `~/.desk/views/<id>.yaml` atomically (ADR 0036). Then `desk.views.open` shows it where the person is,
  with a notice and Undo, and Eris says what she made in one line of soul text.
* **Undo.** `desk.propose.undo` takes back what this session applied, the last by default: it closes
  the view and removes the file (`view.remove`). Undo on the notice runs it; `cmd.undo` can point to it.
* **Entry.** `desk.propose { kind, text }` answers with the outcome. "Make with Eris…" in the palette
  runs it without text: it asks the sentence with a free-text pick and answers at once, because the
  palette cannot show a pick while it waits for the command it runs. The shell's talk line sends
  `/make` sentences, and those that start with "make", "build" or "show me", except a request to
  change the look (`eris/look.ts`, which opens Describe) that names nothing desk.propose makes or
  names the theme (`propose/route.ts`). `mountDesk` installs it, where Eris's soul text is.

### Profiles and key bindings (#340)

The same pipeline, two more kinds, one new rule: what is not a view is previewed on the runtime's own
card, not in desk.views.

* **Card.** `propose/card.ts` floats over the desk and the shell with the same Apply, Try again and
  Discard, and Undo once applied. It is the runtime's because a profile may turn plugins off,
  desk.views among them, and the way back must outlive the switch; the policies it previews are the
  runtime's own code anyway (ADR 0017).
* **Asking.** Both ask through `brain.ask` as views do, each with its own tool: `propose_profile`,
  whose schema is `ProfileContribution` (specs/plugin/v0) without its id, and `propose_key_bindings`,
  whose schema is `{ bindings: KeyBinding[] }` (1 to 20), the one schema of the desk's own, since a
  tool's arguments are an object. A retry after no call repeats each kind's compact schema. The
  profile's context names the installed plugins (name, kind, on or off), the declared scalar settings
  and the profiles; the keys' context names the commands the sentence's words match (at most 20) and
  their keys in force. With every built-in plugin installed the profile's prompt stays far within
  brain.ask's 32000 characters.
* **Profile.** The desk makes the id from the name (`quiet-night`, `-2` when a profile has it), so
  Apply never replaces a profile. Beyond the schema the desk checks that every plugin is installed,
  every setting declared and of its kind, and the shell's layout (`desk.shell.mode`) in shape. The
  card shows a ghost of the desktops it lays out, what turns on and off (as desk.profiles' switch
  would) and which settings change. Apply is `desk.profiles.save` then `desk.profiles.switch`; Undo
  switches back to the profile in force before and removes it with `desk.profiles.remove`.
* **Key bindings.** Every binding names a command the desk has. Conflicts are marked, not refused: a
  key another command has in any layer, two proposals on one key, a binding already there. Apply adds
  them to the person's layer (`desk.keys.bindings`), replacing the person's own entries on those keys;
  Undo writes the layer back exactly. The kind reaches the keymap through one port (`PersonalKeys`),
  so moving keys into the runtime's core (#241) changes one function, and moving saved profiles and
  bindings to files (#286) changes none.
* **Words.** The talk line's routes (`propose/route.ts`) decide whether a sentence goes to
  desk.propose; `propose/talk.ts` picks the kind. "make … profile …" (or build, or `/make`) is a
  profile; "bind … to …" and a make sentence that names shortcuts or key bindings are key bindings;
  the rest are views. A sentence that names a profile or shortcuts is not a look request, look words
  and all. "Make with Eris…" picks the kind the same way when none is given.

### Consequences

* Good, because nothing reaches the disk that neither the desk nor the core accepted, and the person
  saw it first.
* Good, because the next kinds (profiles, key bindings, themes) add a schema, a context, a preview
  and an inverse, not a pipeline.
* Good, because the answer is checked twice, by the core against the tool's schema and by the desk
  against the spec and its names, and the person's conversation with Eris never holds it.
* Bad, because a brain that cannot call the tool (brain-echo knows `propose_theme` and `echo`, not
  `propose_view`, `propose_profile` or `propose_key_bindings`; a model without tool calls) makes
  nothing at all: the desk says so after two asks instead of guessing.
* Bad, because the core drops arguments its schema refuses without saying why, so that retry can only
  repeat the schema, not name the problem; and every ask is a session on the brain (ADR 0059).
* Bad, because the interpreter must learn any keyword a spec adopts; the comparison with Ajv on the
  vectors fails until it does.
* Bad, because the applied view covers Eris in the shell, so the notice on the view says what she
  made too, and Undo is offered only for what this session applied.
* Bad, because the talk line knows English words only; Korean ones are a later change. A sentence that
  is both a look and something to make ("make a board that looks calm") is decided by its words.
* Bad, because previews live in two places: views in desk.views over live data, profiles and key
  bindings on the runtime's card.
* Bad, because Undo of a profile is a switch back: a plugin the proposed profile turned on stays on
  when the earlier profile does not name it.

## More Information

Issue #339; #340 adds profiles and key bindings as kinds, #241 moves keys into the runtime's core,
#286 moves saved profiles and bindings to files, #312 describes a theme, #276 adds `cmd.undo`. ADR
0014 (the brain conversation), 0017 (commands), 0027 (one Eris), 0032 (views are data), 0036 (the
core serves `view.*`), 0059 (`brain.ask`). Until `brain.ask` reached main, this change asked through
`brain.say` with the schema in the prompt; the fallback went with that merge, and profiles and key
bindings came after it.
